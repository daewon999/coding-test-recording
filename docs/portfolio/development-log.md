## 2026-11-23 — 포트폴리오 기록 시작 및 풀이 결과 필터 구현

### 해결하려는 문제

풀이 목록에서 정답 또는 오답 기록만 골라 볼 수 있도록 한다.

### 구현 전 확인한 내용

- `frontend/src/pages/SolutionListPage.tsx`는 최초 진입 시 전체 풀이를 조회하고 표시한다.
- `frontend/src/api/solutionAPI.ts`의 `getAllSolutions()`는 `GET /api/solutions`를 호출한다.
- 백엔드 컨트롤러에는 `GET /api/solutions/correct?correct=true|false`가 이미 정의되어 있다.
- 포트폴리오 기본 문서와 기술 사례 폴더를 생성했다.

### 검토한 설계 선택지

- 프론트엔드 필터: 받은 전체 배열에서 결과에 맞는 풀이를 표시한다. 전환 시 추가 요청이 없지만 전체 데이터 전송량은 줄지 않는다.
- 서버 필터: 기존 결과별 조회 API를 사용한다. 전환 시 요청이 발생하며 로딩·실패·응답 순서 처리가 필요하다. 페이지네이션은 별도 과제다.

### 구현과 선택 이유

- 이미 구현된 결과별 조회 API를 활용하는 서버 필터 방식을 선택했다. 필요한 결과 조건을 서버에 전달하고 반환된 목록을 표시한다. 성능 향상 여부를 측정한 것은 아니다.
- `getSolutionsByCorrect(correct)`를 추가하고, 목록 화면에서 `all`, `correct`, `incorrect` 선택 상태를 관리한다.
- `useEffect`가 필터 변경에 따라 전체 또는 결과별 조회 API를 호출한다.
- 요청 시작 시 로딩과 오류 상태를 초기화하고, effect 정리 시 `ignore`를 설정하여 이전 요청의 늦은 응답이 현재 상태를 덮어쓰지 않도록 했다. 요청 자체를 취소하는 방식은 아니다.
- 선택한 버튼의 스타일과 `aria-pressed`를 적용했다.
- 전체 목록이 비어 있는 경우와 특정 결과의 풀이가 없는 경우의 안내를 구분하고, 필터 결과가 없을 때 전체 풀이로 돌아가는 버튼을 제공한다.

## 2026-11-24 — URL 기반 문제 재사용과 풀이 누적

### 해결하려는 문제와 결정

- 문제 번호가 없는 문제도 등록할 수 있도록 번호를 선택 입력으로 변경했다.
- 플랫폼 + 문제 번호는 동일 문제 판단에 사용하지 않는다.
- 같은 URL이면 기존 문제에 새 풀이를 연결한다. 기존 문제 정보·코드·메모는 덮어쓰지 않는다.
- 제목만 일치하면 후보를 보여주고 기존 문제 선택 또는 별도 문제 생성 여부를 사용자가 결정한다. 플랫폼과 무관하게 후보를 보여주며 기타 플랫폼은 하나의 출처로 간주하지 않는다.

### 구현

- 등록 화면을 `POST /api/solutions/record` 한 번으로 저장하도록 변경했다.
- 문제 조회·필요시 생성·풀이 저장을 서비스의 `@Transactional` 경계에 넣었다.
- 제목 후보 확인 응답에서는 어떤 데이터도 생성하지 않는다. 문제 입력 변경 시 후보 선택을 초기화하고, 서버에서도 선택한 ID가 현재 후보에 속하는지 확인한다.
- URL은 앞뒤 공백, 스킴/호스트 대소문자, 기본 포트를 정리하고 `utm_*`, `fbclid`, `gclid`를 제외한다. 문제 식별용 쿼리, 경로, fragment는 보존한다. HTTP와 HTTPS는 별개의 주소로 취급한다.
- 기존 URL도 같은 규칙으로 비교한다. 이미 같은 URL의 문제가 여러 개 있다면 임의 병합하지 않고 후보 선택을 받는다.
- 제목 비교는 앞뒤 공백과 연속 공백만 정리한다. 제목만 같은 문제는 자동으로 연결하지 않는다.
- 저장 후 상세 화면에 기존 문제에 추가했는지 새 문제를 만들었는지 안내한다.

### 검증

- 프론트엔드 최종 코드: `npm run build`, `npm run lint` 통과.
- 백엔드 초기 구현: Gradle `compileJava` 통과. 이후 후보의 새 문제 생성 가능 여부 응답 필드 등을 추가했으며 최종 백엔드 재컴파일은 미실행.
- H2 테스트 DB 설정 및 통합 테스트 7개 작성: URL 재사용/기존 풀이 보존, 제목 선택, 문제 번호 무시, 식별용 쿼리와 hash 경로 구분, 과거 중복 URL 선택, 잘못된 입력 거부, 풀이 저장 실패 시 문제 생성 롤백.
- 백엔드 테스트는 미실행: 오프라인 캐시에 테스트 의존성이 없고 추가 다운로드 실행 권한 요청이 거절되었다. H2는 테스트 전용이며 실제 서비스 DB에는 테스트를 실행하지 않았다.
- 실제 브라우저와 서비스 DB를 통한 저장 동작 검증은 아직 하지 않았다.

### 현재 한계와 후속 작업

- 기존 문제 전체를 읽고 정규화하여 비교한다. 데이터가 커지면 정규화 URL 컬럼과 인덱스로 이전할 필요가 있다.
- URL의 DB UNIQUE 제약이나 동시 생성 잠금은 추가하지 않았다. 별도 요청이 동시에 최초 등록하면 중복 문제 생성 가능성이 남아 있다.
- 기존 `POST /api/problems`와 `POST /api/solutions`는 호환성을 위해 유지했다. 새 등록 화면만 통합 저장 API를 사용한다.
- 백엔드에서 `gradlew.bat test`로 테스트 의존성을 설치하고 테스트를 실행한 뒤, 실제 화면에서 URL 재등록·번호 없이 등록·제목 후보 선택을 확인한다.
- 문제별 풀이 이력 화면과 기존 중복 데이터 병합은 별도 후속 작업이다.


## 2026-11-24~25 — 풀이 이력 상세, 전체 삭제, 시도 횟수 입력 제거

- 문제별 전체 풀이 삭제 API와 확인창을 추가했다. 서비스 트랜잭션으로 연결된 풀이를 삭제하며 문제 정보는 유지한다.

- DB와 엔티티의 기존 시도 횟수 필드는 호환을 위해 남겼다. 신규 풀이에는 1을 저장하고 수정 시 과거 값을 보존한다. 이 필드는 누적 풀이 수 계산에 사용하지 않는다.
